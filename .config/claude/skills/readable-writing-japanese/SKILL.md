# readable-writing-japanese

## いつ使うか

**人が読む日本語の文章**を書く・レビューする・直すときに発火する:

- Notion ページ / ドキュメント
- GitHub Issue・PR の本文やコメント
- Slack の投稿・スレッド返信
- 設計資料・調査報告・議事録
- プレゼンの原稿やスライド文言

コード・コメント・コミットメッセージ本文の生成そのものは対象外（ただし PR 本文は対象）。

**目的**: 読み手が最小の労力で要点をつかめる文章にする。書き手が楽な文章ではなく、読み手が楽な文章を書く。

## 原則

1. **結論を先に**: 一番言いたいことを冒頭に置く。前置き・経緯から始めない
2. **簡潔に**: 1 文 1 メッセージ。1 文が長くなったら分割する。目安 60〜80 字
3. **冗長表現を排除**: 意味を足さない語・回りくどい言い回しを削る（後述の一覧）
4. **具体的に**: 「いくつか」「なるべく早く」ではなく数値・日付・対象を書く
5. **構造化**: 3 項目以上の並列は箇条書き、比較は表にする。ダラダラした散文にしない
6. **能動・断定**: 「〜されると思われる」より「〜する」。責任の所在と主語を曖昧にしない

## 日本語特有の観点

日本語ならではの読みやすさを整える:

- **漢字とかなのバランス**: 漢字を並べすぎない。「出来る→できる」「事→こと」「為→ため」「様々な→さまざまな」など、副詞・形式名詞・補助動詞はひらく
- **句読点**: 読点は 1 文に 2〜3 個まで。意味の切れ目に打ち、修飾の係り先を明確にする
- **助詞の重複を避ける**: 「〜の〜の〜の」と「の」を連ねない。「は」と「が」を使い分ける
- **一文の主述を近づける**: 日本語は述語が末尾に来るので、長い修飾で主語と述語を離しすぎない
- **体言止めの多用を避ける**: リズム付けの体言止めは効果的だが、連発すると内容が曖昧になる
- **カタカナ語・英略語**: 読み手が知らない語は初出で補足する。社外向けは特に
- **表記ゆれをなくす**: 「サーバー / サーバ」「ユーザー / ユーザ」など、1 文書内で統一する

## 冗長表現の削減リスト

書いた後に必ず見直し、以下を置換・削除する:

| 冗長 | 簡潔 |
|---|---|
| 〜することができます | 〜できます |
| 〜という形になります / 〜となっております | 〜です |
| 〜させていただきます | 〜します |
| 〜する必要があると考えられます | 〜する必要があります |
| 〜については | 〜は |
| 〜に関して / 〜に関しましては | 〜は / 〜について |
| 行うことが可能です | できます |
| 現時点においては | 今は / 現在は |
| 〜というふうに | 〜と |
| 基本的には / 一般的には（無意味なとき） | （削除） |
| まず最初に | まず / 最初に |
| 各々の / それぞれの（自明なとき） | （削除） |
| 〜というものは | 〜は |
| 〜する形で対応します | 〜します |

- **二重否定を避ける**: 「〜できないことはない」→「〜できる」
- **同義語の重複を避ける**: 「まず最初に」「必ず必須」「約〜程度」「後で後述」
- **主語と述語の距離を縮める**: 長い修飾を先に置いて主述を離さない
- **接続詞の乱用を避ける**: 「そして」「また」「なお」を各文頭に付けない
- **一文一義**: 「〜だが、〜で、〜なので、〜」と接続で伸ばさず切る

## 媒体ごとの調整

| 媒体 | 重視する点 |
|---|---|
| Slack | 冒頭に結論と依頼（何をしてほしいか）。長文はスレッドに畳む。絵文字は最小限 |
| GitHub Issue | 背景 → 現状 → 期待 → 再現手順の順。見出しで区切る |
| GitHub PR | 何を・なぜ変えたかを 1〜2 行で。差分から自明なことは書かない。リポジトリに PR テンプレートがあれば基本的に従って本文を書く |
| Notion / 設計資料 | 冒頭に TL;DR / 概要。見出しと目次で読み飛ばせる構造に |
| 調査報告 | 結論 → 根拠 → 補足。open question を明示 |
| プレゼン | 1 スライド 1 メッセージ。文ではなくキーフレーズ |

## 処理手順

1. **対象と媒体を把握**: どの媒体向けか。読み手は誰か（社内 / 社外、技術者 / 非技術者）
2. **要点を先に決める**: 一番伝えたい 1 文を確定してから書き出す
3. **ドラフトを書く**: 原則に沿って構造から組む
4. **削る**: 冗長表現リストで 1 パス。声に出して読めない長文は切る
5. **確認**: 下記チェックリストを通す
6. 既存文章のリライト依頼なら、**変更前後の差分と、どの原則で直したかを簡潔に添える**

## チェックリスト（出す前）

- [ ] 結論・要点が冒頭にあるか
- [ ] 1 文が長すぎないか（60〜80 字目安、複数メッセージを詰めていないか）
- [ ] 冗長表現リストの語が残っていないか
- [ ] 「いくつか」「なるべく」等の曖昧語を具体化したか
- [ ] 3 項目以上の並列を箇条書き・表にしたか
- [ ] 漢字を並べすぎず、表記ゆれがないか（1 文書内で統一）
- [ ] 削っても意味が変わらない語・文が残っていないか
- [ ] 媒体に合った構造・トーンか

## やってはいけないこと

- ❌ **前置きの長文**: 「お疲れ様です。表題の件ですが〜」で本題を遅らせない
- ❌ **情報の水増し**: 内容が薄いのを丁寧語や修飾で埋めない
- ❌ **過度な敬語・クッション**: 「恐れ入りますが」「もしよろしければ」の連発
- ❌ **絵文字・装飾での誤魔化し**: 構造で読みやすくする。装飾で飾らない
- ❌ **元の意図の改変**: リライトで筆者の主張・ニュアンスを勝手に変えない
- ❌ **作業経緯のコメント**: 「レビュー指摘対応」など、なぜ書いたかの経緯を本文に残さない。読み手に不要
- ❌ **環境依存文字**: 丸数字（①②）・㈱・ローマ数字（Ⅰ Ⅱ）・半角カナなど、環境で化ける文字は使わない

## 指摘を受けたときの学習（重要）

ユーザから文章について指摘・修正・好みを示されたら、**この skill を更新する候補として扱う**。

### 手順

1. 指摘を一般化できるか判断する
    - 一度きり・その文脈限定 → skill 更新はしない（その場で直すだけ）
    - 繰り返し適用できる規則（言い回しの癖、媒体別の好み、削るべき定型句）→ 更新候補
2. 更新候補なら、**この SKILL.md への追記・修正案を提示して確認を取る**
    - 例:「『冗長表現の削減リスト』に『〜のような形 → 〜』を追加します。よいですか？」
    - どのセクションに、何を、なぜ追加するかを 1〜2 行で示す
3. 承認されたら `Edit` で SKILL.md を更新する。**勝手に書き換えず必ず確認してから**
4. 追加先が既存セクションに無ければ新セクションを作ってよい

### 更新の粒度

- 冗長な言い回しの指摘 → 「冗長表現の削減リスト」に 1 行追加
- 媒体固有の好み → 「媒体ごとの調整」に追記
- 全体方針の指摘 → 「原則」を見直す
